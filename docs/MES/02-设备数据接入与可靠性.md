# 设备数据接入与可靠性

## 1. 职责边界

### HTHIUM 单机端负责

- PLC实时采集和数据质量判断。
- 本机报警触发/恢复判断。
- 快照前后帧冻结。
- 形成业务消息并先写入本地待发送表。
- 按优先级上传、失败重试、成功确认。

### MES 服务端负责

- 验证设备身份、字段、协议版本和消息大小。
- 幂等接收、原始消息留存、业务表转换。
- 识别顺序缺口、重复、延迟、坏数据和时钟异常。
- 向客户端返回可执行的接收结果。
- 提供查询、统计、审计和前端实时通知。

MES 不应在设备运行过程中直接轮询 PLC，避免中心故障影响设备。

## 2. 统一消息信封

```json
{
  "messageId": "01J...ULID或UUID",
  "messageType": "alarm.triggered",
  "schemaVersion": "1.0",
  "siteCode": "SITE-01",
  "lineCode": "LINE-01",
  "deviceCode": "SEALPIN-01",
  "sequenceNo": 1024,
  "occurredAt": "2026-09-18T10:30:00.123+08:00",
  "sentAt": "2026-09-18T10:30:00.300+08:00",
  "quality": "Good",
  "traceId": "可选链路ID",
  "payload": {}
}
```

字段规则：

- `messageId`：在单机第一次创建时生成，重试时保持不变。
- `messageType`：小写分段命名，例如 `alarm.triggered`。
- `schemaVersion`：决定payload验证规则。
- `sequenceNo`：每台设备单调递增，重启后从本地持久值继续。
- `occurredAt`：业务在设备端发生的时间。
- `sentAt`：实际发出时间。
- 服务端另存 `receivedAt`，不得覆盖设备时间。

## 3. 客户端持久化发送队列

建议单机新增 `central_outbox_message`：

| 字段 | 用途 |
|---|---|
| id | 本地主键 |
| message_id | 全局消息ID，唯一索引 |
| message_type | 消息类型 |
| priority | 报警高于普通状态 |
| payload_json | 完整待发送消息 |
| status | Pending/Sending/Succeeded/DeadLetter |
| retry_count | 重试次数 |
| next_retry_at | 下次重试时间 |
| last_error | 最近错误摘要 |
| created_at | 创建时间 |
| sent_at | 成功时间 |

流程：

```text
业务事件产生
  → 与本机业务记录同一事务写入Outbox
  → 后台上传服务取Pending消息
  → 发送MES
  ├─ 成功：标记Succeeded/按策略清理
  ├─ 可重试错误：计算next_retry_at
  └─ 永久错误：进入DeadLetter等待人工处理
```

不允许在 PLC 扫描线程或 UI 线程同步等待 MES 返回。

## 4. 重试策略

- 网络超时、HTTP 408、429、5xx：重试。
- HTTP 400字段错误：不自动无限重试，进入死信并记录原因。
- HTTP 401/403：暂停该设备上传并产生配置告警。
- HTTP 409重复消息：如果服务端明确表示已接收，客户端可视为成功。
- 退避建议：2秒、5秒、10秒、30秒、1分钟、5分钟，之后按配置周期重试。
- 增加随机抖动，防止多设备同时恢复造成补传风暴。

## 5. 幂等和事务

服务端接入表建立唯一约束：

```text
UNIQUE(device_code, message_id)
```

同一消息重复上传时：

- 不重复生成报警、产量或质量记录。
- 返回之前的接收结果。
- 记录重复次数用于诊断，但不把正常重试记作错误。

原始消息和业务记录应在同一数据库事务内完成，或使用 Inbox/Outbox 状态机保证可补偿。

## 6. 顺序与缺口处理

服务端保存每台设备最近确认的 `sequenceNo`：

- 新序号 = 上次 + 1：正常。
- 新序号 <= 上次：重复或乱序，仍按messageId幂等处理。
- 新序号 > 上次 + 1：创建缺口记录，等待客户端补传。
- 客户端重装或序号重置：通过新的 `clientInstanceId` 区分实例。

顺序号用于发现丢失，不作为数据库主键，也不能代替 `messageId`。

## 7. 批量补传

正常实时数据可以单条发送；断线恢复使用批量接口：

```text
POST /api/v1/edge/messages/batch
```

建议初始限制：

- 每批不超过100条。
- 同时限制压缩前后字节数。
- 返回逐条结果，不能因为一条坏数据让整批永久失败。
- 报警类实时消息与历史补传使用不同并发通道。

具体数值在性能测试后配置化，不写死在业务代码。

## 8. 数据质量

统一质量状态建议：

```text
Good                正常可信
Uncertain           可用但存在风险
Bad                 无效数据
Disconnected        PLC或数据源断开
Stale               超过允许时间未更新
OutOfRange          超过工程范围
TimestampInvalid    时间戳异常
SequenceGap         存在序列缺口
```

服务端不能把质量差的数据悄悄当作0；数值、质量和采集时间必须一起保存。

## 9. 时钟策略

- 所有接口使用带时区偏移的 ISO 8601 时间。
- 数据库存储统一UTC，显示时转换为Asia/Shanghai。
- 保存 `occurredAt`、`sentAt`、`receivedAt` 三个时间。
- 当设备时间与服务端偏差超过阈值时标记 `TimestampInvalid`，但仍保留原始数据。
- 生产环境通过局域网NTP统一设备和服务器时钟。

## 10. 流量保护

- 请求体大小限制。
- 单设备和单IP限流。
- 有界处理队列，满载时返回429而不是耗尽内存。
- 数据库连接池和批量写入大小有上限。
- 快照上传独立限制，避免大JSON挤占心跳和报警请求。
- 服务端停机或数据库异常时不得返回假成功。
