# 总体架构与技术路线

## 1. 系统定位

HTHIUM MES 是局域网中心服务，不直接读取每台设备 PLC。PLC 通讯、实时采集、报警判定和本机保护继续由 HTHIUM 单机上位机完成；MES 接收已经结构化的数据，完成集中存储、跨设备查询、看板、追溯和调度。

这种边界能够保证 MES 或网络故障时，设备本机采集和控制不受影响。

## 3. 后端技术选型

| 能力 | 选型 | 采用原因 | 第一阶段是否启用 |
|---|---|---|---|
| 运行时 | .NET 10 LTS | 本机已安装，长期支持，适合新系统 | 是 |
| Web框架 | ASP.NET Core Web API | 高性能、DI/配置/日志/健康检查完整 | 是 |
| 接口组织 | Controller + 模块路由 | MES接口多，便于供应商理解和权限标注 | 是 |
| API文档 | ASP.NET Core OpenAPI | 由代码生成契约，支持前端生成客户端 | 是 |
| 数据库 | MySQL独立库 `hthium_mes` | 与现有技术栈一致，便于运维 | 是 |
| ORM | SqlSugar | 团队已有代码和经验，降低迁移成本 | 是 |
| 实时推送 | SignalR | 向前端推送在线状态和实时报警 | 预留，M3启用 |
| 后台处理 | `BackgroundService` + 有界Channel | 异步处理、削峰、补偿，无需先上MQ | 是 |
| 分布式缓存 | Redis | 多实例会话、热点缓存、分布式锁 | 暂不启用 |
| 消息队列 | RabbitMQ等 | 系统解耦、跨系统可靠消费 | 达到触发条件再引入 |
| 用户认证 | ASP.NET Core Identity/JWT | 标准密码散列、角色与接口鉴权 | M3启用 |
| 设备认证 | Device API Key + HMAC/HTTPS | 每台设备可独立吊销和审计 | M1启用 |
| 测试 | xUnit + 集成测试 | 保证契约、幂等和数据库行为 | 是 |

不建议第一阶段同时引入 MediatR、Redis、RabbitMQ、微服务和容器编排。只有明确解决实际问题的组件才加入系统。

## 4. 模块化单体边界

```text
Identity        用户、角色、权限、设备凭据
MasterData      工厂、产线、设备、产品、工艺基础数据
Ingestion       消息接入、校验、幂等、原始消息、顺序检查
Equipment       心跳、在线状态、设备状态、停机状态
Alarm           报警触发、恢复、确认、闭环和统计
Production      工单、批次、产品过站、产量和节拍
Quality         检测结果、不良代码、质量判定和追溯
Snapshot        PLC快照元数据、点位定义和帧数据
Dashboard       看板聚合查询和实时推送
Audit           操作日志、接口日志和配置变更历史
Integration     ERP/WMS/QMS等外部系统适配
```

模块之间通过应用服务和领域事件协作，不允许 Controller 直接访问其他模块数据表。

## 5. 建议的代码结构

```text
HTHIUM.Mes.sln
├── src
│   ├── HTHIUM.Mes.Api
│   ├── HTHIUM.Mes.Application
│   ├── HTHIUM.Mes.Domain
│   ├── HTHIUM.Mes.Infrastructure
│   └── HTHIUM.Mes.Contracts
├── tests
│   ├── HTHIUM.Mes.Tests.Unit
│   └── HTHIUM.Mes.Tests.Integration
├── deploy
│   ├── windows-service
│   └── database
└── docs

HTHIUM.Mes.Web
├── src/api              OpenAPI生成的接口客户端
├── src/modules          设备、报警、生产、质量等业务模块
├── src/router           页面路由与权限守卫
├── src/stores           用户和全局状态
└── src/views            浏览器页面
```

依赖规则：

- Domain 不依赖数据库、HTTP或任何界面技术。
- Application 只依赖 Domain 和抽象接口。
- Infrastructure 实现数据库、文件、缓存和外部接口。
- Api 负责启动、认证、中间件和端点，不存放业务规则。
- Contracts 只保存跨进程DTO和协议枚举，不复用数据库实体。

## 6. 请求处理链路

```text
HTTP请求
  → TraceId/访问日志
  → HTTPS与大小限制
  → 设备认证/用户认证
  → DTO反序列化与字段校验
  → 消息幂等检查
  → 原始消息入库
  → 业务数据事务处理
  → Outbox记录
  → 返回接收结果
  → 后台统计/SignalR推送
```

API 返回成功的含义必须明确：消息已经可靠入库，而不是只进入进程内队列。

## 7. 浏览器前端技术路线

正式 MES 使用浏览器作为唯一业务和运维界面，建议采用：

- Vue 3 + TypeScript + Vite。
- Pinia 管理用户、权限和全局状态。
- Vue Router 管理模块路由。
- Element Plus 或同类企业组件库，最终只选一套。
- ECharts 展示产量、报警、节拍、OEE和趋势。
- OpenAPI 自动生成 TypeScript API 客户端，避免手写接口字段。
- SignalR 只承载状态变化和通知，历史数据仍通过分页 HTTP API 查询。
- 设备监控、接口状态、服务健康、日志查询和系统配置都在Web管理端实现，不再开发Central WPF版本。
- 前后端采用独立工程和独立构建；简单部署时可将前端静态产物交由ASP.NET Core或反向代理统一发布。

## 8. 部署路线

### 本机开发

- API：`https://localhost:端口`。
- MySQL：本机独立 `hthium_mes_dev`。
- HTHIUM：连接本机接口完成闭环。

### 局域网测试

- MES API 安装为 Windows Service。
- 使用固定服务器IP和正式设备编码。
- MySQL仅允许MES服务器访问。
- HTHIUM通过HTTPS连接服务器，不直接访问MES数据库。

### 正式生产

- API、数据库分开部署或至少分开进程和账号。
- Windows Service 自动启动和失败恢复。
- 数据库每日备份、恢复演练、磁盘阈值告警。
- 所有补丁先通过测试环境验证。

## 9. 后续扩展触发条件

出现以下情况才考虑 Redis：多实例部署、共享会话、热点查询数据库压力明显。

出现以下情况才考虑消息队列：外部系统消费者增加、单次流量峰值无法由有界Channel吸收、需要跨服务独立重放。

出现以下情况才拆微服务：某模块需独立发布/扩容、团队能独立维护、数据库边界和消息契约已经稳定。
