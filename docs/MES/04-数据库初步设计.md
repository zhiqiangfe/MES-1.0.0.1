# 数据库初步设计

## 1. 数据库边界

- MES数据库：`hthium_mes`。
- HTHIUM单机数据库：每台设备本地 `hthium_demo` 或设备独立库。
- HTHIUM只能通过API访问MES，不允许直连MES数据库。
- MES不直接连接各单机数据库。

## 2. 表分组

## 3. 核心关联

```text
mes_site 1 ── N mes_line 1 ── N mes_device
                                  │
                                  ├── N mes_ingest_message
                                  ├── 1 mes_device_state
                                  ├── N mes_device_heartbeat
                                  ├── N mes_alarm_event
                                  ├── N mes_production_record
                                  ├── N mes_quality_record
                                  └── N mes_plc_snapshot

mes_ingest_message 1 ── 0..1 具体业务记录
mes_alarm_event    1 ── 0..N mes_plc_snapshot
mes_plc_snapshot  1 ── N mes_plc_snapshot_point
mes_plc_snapshot  1 ── N mes_plc_snapshot_frame
```

业务记录保留 `ingest_message_id`，可以追溯到客户端原始报文。

## 4. `mes_ingest_message`建议字段

```text
id                    bigint主键
message_id            varchar，全局消息ID
message_type          varchar
schema_version        varchar
site_code             varchar
line_code             varchar
device_code           varchar
client_instance_id    varchar
sequence_no           bigint
occurred_at_utc       datetime(6)
sent_at_utc           datetime(6)
received_at_utc       datetime(6)
quality               varchar
payload_json          json/longtext
payload_hash          varchar
process_status        varchar
process_error_code    varchar
process_error_message varchar
retry_count           int
created_at_utc        datetime(6)
```

核心索引：

```text
UNIQUE(device_code, message_id)
INDEX(device_code, sequence_no)
INDEX(message_type, received_at_utc)
INDEX(process_status, received_at_utc)
```

## 5. 报警模型

报警使用一条生命周期记录，至少保存：

- alarm_record_id：服务端主键。
- source_alarm_id：单机报警记录ID。
- alarm_code、alarm_name、category、severity。
- triggered_at_utc、recovered_at_utc。
- trigger_ingest_message_id、recover_ingest_message_id。
- station_name、device_code、line_code。
- status：Active/Recovered/Acknowledged/Closed。
- acknowledged_by、acknowledged_at、cause、action。

服务端以设备、源报警ID或明确的生命周期标识关联触发与恢复，不能只按报警名称匹配。

## 6. PLC快照存储

不建议把全部快照长期塞入一列巨大JSON后直接做业务查询。第一阶段可采用混合模式：

- `mes_plc_snapshot` 保存快照头和参数定义副本。
- 帧数据量较小时，`mes_plc_snapshot_frame.frame_json` 保存一帧。
- 需要曲线查询的关键数值可拆为窄表或后续时序存储。
- 原始JSON保留用于证据追溯，统计字段单独列化。

快照必须保存当时的参数名称、地址、数据类型、单位和排序副本，不能在查看历史时重新依赖已经修改的配置表。

## 7. 生命周期和归档

建议初始策略，最终根据真实数据量修订：

- 设备最新状态：永久保留当前值。
- 心跳明细：在线库保留1～3个月，日统计长期保留。
- 原始接入消息：保留3～6个月或按审计要求。
- 报警和生产记录：按业务追溯要求长期保留。
- PLC快照：热数据3个月，之后压缩归档。
- API成功日志：短期或采样；失败和安全日志保留更长。

删除必须按小批次执行，避免一次大事务锁表。归档任务记录执行批次、影响行数和失败原因。

## 8. 数据库变更规则

- 禁止生产环境由应用启动时静默修改表结构。
- 使用有版本的SQL迁移脚本。
- 每次迁移包含升级、校验和必要的回滚说明。
- 上线前备份并在测试数据库演练。
- 应用启动只检查版本，不自动删除或重建业务表。
